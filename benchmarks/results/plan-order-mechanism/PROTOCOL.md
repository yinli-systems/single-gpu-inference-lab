# Metadata-only FA2 ordering: frozen protocol, 2026-09-29

Question: does work-descriptor order change attention execution time with identical physical Q/K/V, output buffers, plan sizing and merge destinations? This is NOT another physical row-repacking experiment.

## Source and scope
Pinned FlashInfer 0.6.18 wrapper SHA256 743953a8d301d89c6943dc48a8f6b393c0d636b71b165ae1842c2c65c7defaab. FA2,32/8 heads,D128,FP16/BF16,512 MiB workspace per isolated wrapper. Eager-created plans and fixed-shape CUDA-graph replays are distinct timings. Dynamic/padded graph plans are explicitly rejected, including the historical mask failure addressed by already-merged upstream PR5176. No live engine/runtime installation is changed.

Descriptor triples (request,query-tile,KV-tile) are permuted as complete bijections. Per-request output/merge destinations, chunk size, grid dimensions, input/output addresses and plan scalars remain unchanged. Full output and LSE must match the unmodified plan BIT FOR BIT in eager and graph execution. Independent selected FP32 vectors check semantics. Failures stop the job and remain on disk.

## Policies and data
Primary candidate is heavy_first: descending estimated causal visible-key work per query tile. This is an existing scheduling heuristic applied as a falsifiable intervention, not a new algorithm claim. Request-reverse and interleave are explanatory. Identity-repeat is the identical native descriptor order, an A/A control.

Discovery: the prior n2,n4,n8,n16 same/opposite and equal-work witnesses. These do not count as held-out wins. Holdout: eight fixed configurations with n=3,3,5,5,7,7,9,9, generated by Random(20261103), each in same/opposite pairing. Fixed before new GPU timing; no shape search after results.

Two one-GPU canaries first, one per family. Formal launch only after both have complete qualification and exact-output checks. Then three process repetitions per GPU family, two dtypes, auto/unsplit, eager/graph, six randomized matched blocks after one unscored block. Maximum two formal jobs concurrently per family. Jobs have a15-minute wall limit. No resource purchases or cancellation of other jobs.

## Endpoints and interpretation
Report all policies and all cells. Primary is equal-weight held-out CUDA-graph heavy_first/native geometric-mean ratio per GPU family, plus dtype and split breakdowns. Conditional95% intervals bootstrap the three process repeats and matched blocks; no hardware-population or multiplicity-adjusted theorem. A/A equivalence must be checked with90% intervals within max(3us,2% native latency); failed controls remain visible and block promotion.

This prototype copies and validates metadata outside the run timer; apply/setup time is recorded separately. Run-only speedups cannot be called total-cycle or serving speedups. No serving promotion is possible from this experiment. A potentially useful run-path result requires a separate source-integrated implementation that charges planning/reordering overhead and an actual complete-engine test.

No warmup, failure, negative control or unfavorable subgroup is silently removed. Any source/oracle repair retains the first canary failure and binds the replacement source to a new commit before formal execution. Current full-engine-v2 remains NOT PROMOTED.
