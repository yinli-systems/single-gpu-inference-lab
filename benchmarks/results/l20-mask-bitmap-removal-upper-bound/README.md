# Negative result: removing #54901's residual bitmap buys nothing end-to-end (L20)

**Question.** vLLM #54901 (0.29.1+) returns the sampling mask as compact `[B, max_top_k]` IDs but
still produces and copies the full `[B, ceil(V/8)]` bitmap every step as the exact fallback for
rows whose support exceeds the compact width (top-k boundary ties). The path microbenchmark
([`../l20-support-pack-path/`](../l20-support-pack-path/README.md), `raw-with-main.json`) puts that
residual at 0.66 ms vs 0.32 ms per step at batch 256. Is any of it on the serving critical path,
i.e. would a "compact IDs + overflow flag + conditional exact fallback" design be worth building?

**Method.** Upper bound first, design second. `vllm-main-skip-bitmap-experiment.patch` adds an
env-gated variant of `SamplingMaskTensors.from_logits` that runs an IDs-only kernel and never
allocates, fills or copies the bitmap (`VLLM_MASK_SKIP_BITMAP=1`); a row whose support exceeds the
compact width raises instead of falling back. This is *not* exact and is not proposed as a change;
it measures the most any conditional-fallback scheme could recover. Same harness and workload as
the other artifacts (256-token rollouts, `ignore_eos`, `top_k 50 / top_p 0.95`, generate API, 3
interleaved rounds, `gen` requests), at concurrency 64 (128 prompts) and 256 (512 prompts).
vLLM 0.29.0 + #54901 backported; commit `03bdc7a`, clean tree.

## Result (tok/s, median of 3 rounds, min–max)

| Model | Concurrency | `mask_upstream` (#54901) | `mask_nobitmap` (upper bound) | `native` |
| --- | ---: | ---: | ---: | ---: |
| Qwen2.5-0.5B | 64 | 16,450 (14,872–16,647) | 16,398 (14,449–16,503) | 17,784 (17,514–18,668) |
| Qwen2.5-0.5B | 256 | 19,767 (18,556–20,203) | 19,641 (19,494–20,739) | 22,847 (21,759–23,260) |
| Qwen3-4B | 64 | 3,511 (3,220–3,521) | 3,491 (3,222–3,516) | 3,480 (3,241–3,524) |
| Qwen3-4B | 256 | 4,278 (3,899–4,285) | 4,305 (3,890–4,308) | 4,277 (3,918–4,342) |

Differences between `mask_upstream` and `mask_nobitmap` are inside round-to-round noise in all four
cells. No overflow was hit (the experiment would have raised).

## Conclusion

The bitmap's GPU write and its 4.9 MB/step D2H at batch 256 are fully hidden behind vLLM's async
output pipeline on this host; they are GPU-time and copy-engine time, not critical-path latency.
A conditional-fallback design has no measurable cost to remove here and is **not pursued**. The
0.5B model's remaining mask gap (0.86–0.87x of native at both concurrencies; 4B is at parity) is
therefore elsewhere — the per-request mask list assembly and JSON on the API server, and the
scheduler's per-request slicing — which is what #54901's own description calls "frontend work
proportional to the number of finished requests".

This is the stopping rule from the research plan applied: measure the removable cost in the real
critical path before writing the kernel; when it is zero, keep the finding and redirect.
